## 1. 模型与任务

| 术语 | 人话 | 本项目里的例子 |
|---|---|---|
| **检测 Detection** | 回答"**在哪**"，输出一串框 | 边缘 v9t 画出的红色矩形 |
| **分类 Classification** | 回答"**是什么**"，输出一个类别 | 云端判断裁出来的那块是 crazing |
| **两阶段检测 Two-stage** | 先找位置，再判类别，分两步走 | 这正是我们"边缘给框 + 云端 ROI 分类"的架构 |
| **框 / bbox** | 圈住缺陷的矩形 | 标签 `0 0.28 0.79 0.54 0.30` 就是一个框 |
| **置信度 confidence / conf** | 模型"**有多大把握**"，0–1 | `conf=0.87` = 87% 把握 |
| **阈值 τ / tau** | "把握到多少**才敢下结论**" | τ=0.5 就是"没到一半把握就不报" |
| **IoU** | 两个框**重叠面积 ÷ 合并面积**，>0.5 通常算"画对了" | 评估时用它判断模型框和标注框是否匹配 |
| **NMS 非极大值抑制** | 同一个缺陷被画了好几个框，**只留最靠谱的那个** | ultralytics 推理时默认开启 |
| **ROI** | Region of Interest，从大图里**裁下来的那一小块** | 把边缘画的框裁出来喂给云端分类器 |
| **输入尺寸 imgsz** | 喂给网络的图被缩放到多大 | 边缘 640、云端 960（目前），ROI 214/224 |
| **stride / 下采样倍数** | 网络每走几步把图缩一次，**P3 层 = 8，P5 层 = 32** | 一个 92px 的框在 P3 上只占 92÷8 ≈ 11.5 个格子 |
| **backbone / neck / head** | 网络的"身体/脖子/头"：提特征 / 融合 / 出结果 | 改 P2 头改的就是 head 和 neck 的接线 |
| **ONNX** | 模型的**通用文件格式**，像 PDF，谁都能打开跑 | `models/YOLOv9t/yolov9t_best.onnx` |
| **权重 weights / best.pt** | 训练出来的"参数文件"，几十 MB 到几百 MB | 不进 git，走网盘传 |
| **预训练 / 微调** | 先在 COCO 这种大库上学会"看图"，再用我们的数据调 | 我们所有模型都是微调来的 |
| **过拟合** | 训练集背得滚瓜烂熟，新图一塌糊涂 | 1800 张数据训大模型（v8m）容易这样 |
| **数据增强** | 把图翻转、调亮度、裁剪，凭空造出更多训练样本 | 小目标任务里很关键 |
| **混淆矩阵** | 一张 **N×N 的表**，行是"真实类别"，列是"模型说的"，**对角线上才是对的** | 用来看 crazing 被认成了谁 |

## 2. 评估指标（最容易搞错的一块）

| 术语 | 人话 | 本项目里的例子 |
|---|---|---|
| **GT（Ground Truth）** | **标准答案**，人工标注的 | `labels/val/*.txt` |
| **TP / FP / FN** | 抓对了 / 冤枉了 / **漏掉了** | 抓对 15、冤枉 3、漏 5 |
| **Precision 精确率** | **报出来的里面几成是真的** | 报 18 个，15 个对 → P = 83% |
| **Recall 召回率** | **该抓的抓到了几成** | 该抓 20 个，抓到 15 → R = 75% |
| **漏报 / 漏检** | 有缺陷但没报（**工业上最严重**） | 对应 FN |
| **误报 / 虚警** | 没缺陷却报了（**可以接受**） | 对应 FP |
| **FPPI** | **平均每张图冤枉几个** | 3 个虚警 ÷ 360 张图 = 0.008 |
| **FROC 曲线** | 横轴 FPPI、纵轴 Recall 的折线图，**越靠左上越好** | 我们用它替代 mAP 做主图 |
| **工作点 operating point** | 阈值固定在某一个值时的那一组 (R, FPPI) | "conf=0.5 时 R=69%" 就是一个工作点 |
| **P-R 曲线** | 阈值从松到严扫一遍，P 和 R 此消彼长的折线 | 和 FROC 类似的思路，但横轴是 R |
| **AP** | P-R 曲线下的面积，**单个类别的综合分** | `AP50_crazing = 0.395` |
| **mAP50** | 把 IoU 门槛定在 0.5 时，六类 AP 的平均 | 我们最好 0.7607（v9t） |
| **mAP50-95** | IoU 从 0.5 到 0.95 每隔 0.05 算一次再平均，**很严格** | 我们最好 0.4257（v9t） |

> **为什么 mAP50-95 只有 0.42 不是模型的锅**：老师说"目标检测要求标注大致的范围"，意思是 GT 框本来就不精确。拿 0.95 这种严苛 IoU 去量，量的是标注质量，不是模型水平。

## 3. 系统与工程

| 术语 | 人话 | 本项目里的例子 |
|---|---|---|
| **云边协同** | 边缘先筛、云端再判，**两级配合** | 我们的整体架构 |
| **路由 Routing** | **分诊台**，决定这张图要不要上云 | `decide(features) -> action` |
| **端到端延迟** | 一张图从进来到出结果，**总共多久** | p50 = 46.5ms（全边缘时） |
| **分段延迟** | 把总时间**拆成几段**分开记 | 边缘 / 编排 / 网络 / 云端 四段 |
| **p50 / p95 / p99** | 100 张图按耗时排队，**第 50 / 95 / 99 张的耗时** | p95=540ms 意味着"最慢的那 5% 慢得离谱" |
| **RTT** | Round Trip Time，**数据寄到对面再寄回来**的时间 | 我们模拟 80ms |
| **缓存 cache** | 把跑过的结果**存成表格**，下次不用重跑 | `cache.json`、`cache_v2.json` |
| **接口契约** | 两个人搭伙，**先说好"我交给你什么、你还我什么"** | `router/README.md` 里的字段定义 |
| **压测** | 让**很多请求同时来**，看系统会不会崩 | 100 并发测 `/recheck` |
| **并发** | 同一时刻有多少个请求在跑 | 100 并发 ≈ 100 个人同时上传 |
| **吞吐 throughput** | **单位时间能处理多少张** | 产线 30 件/分钟 = 0.5 件/秒 |
| **基线 baseline** | **及格线 / 对照组**，用来证明你比它强 | 固定阈值 τ 法就是基线 |

> **端到端延迟 vs 吞吐**：一个人等 0.5 秒（延迟），和一分钟能过 120 件（吞吐），是两件事。产线真正卡的是吞吐，但单张太慢也会拖垮吞吐。

## 4. 数据

| 术语 | 人话 | 本项目里的例子 |
|---|---|---|
| **NEU-DET** | 东北大学热轧带钢表面缺陷数据集，**工业质检的标准基准** | 我们的 1800 张图 |
| **YOLO 标签格式** | 一行 = `类别 中心x 中心y 宽 高`，**数值都除以了图宽/图高** | `0 0.2825 0.7875 0.535 0.295` |
| **归一化坐标** | 坐标都变成 0–1 之间的小数，**跟图片尺寸无关** | 所以面积占比 = 宽 × 高，直接可得 |
| **train / val / test split** | 训练集 / 验证集 / 测试集，**三者不能重叠** | 我们 train 1440、val 360 |
| **数据泄露** | 训练集里混进了验证集的图，**分数虚高，一上真实场景就露馅** | 已检查：同名文件重叠 = 0 |
| **多类共现** | 一张图里同时有两类缺陷 | 63 张图有 inclusion 但名字不叫 inclusion |
| **小目标** | COCO 的定义：面积 < 32×32 像素 | 我们最小的是 inclusion，中位 40×40，**几乎够不上小目标** |
| **背景图 / 负样本** | 一张缺陷都没有的正常图 | **我们一张都没有**，所以算不出传统误报率 |

## 5. 路由与强化学习

| 术语 | 人话 | 本项目里的例子 |
|---|---|---|
| **bandit 老虎机** | 几台老虎机不知道哪台出钱多，**边拉边学** | 每张图 = 一次"拉杆"，送不送云 |
| **上下文 bandit** | 拉杆之前**先看一眼这张图的特征**再决定 | 看 conf、框大小，决定送不送 |
| **DQN** | 深度 Q 网络，**连续决策**的强化学习 | 等有了队列再上，现在不用 |
| **state / action / reward** | 状态 / 动作 / 奖励，强化学习三件套 | 状态=图特征+队列，动作=送不送，奖励=翻转得分 |
| **序列决策** | 当前决定会**影响下一步** | 有队列时：这单送云会让下单调慢 |
| **oracle 上界** | **开天眼的最优解**，只用来算"理论上还能好多少" | 5% 预算下最多救 18 次翻转 |
| **预算 budget** | 允许上云的**名额比例** | 5% = 360 张里只有 18 张能上云 |
| **约束优化** | 在"不超过某条线"的前提下，把另一个指标做到最好 | 在 p95 ≤ 100ms 下最大化 Recall |

## 6. 五个最容易搞错的认知（必看）

| ❌ 错误认知 | ✅ 正确说法 |
|---|---|
| mAP = Precision × Recall | **AP 是 P-R 曲线下的面积**，是 P 和 R 整个变化过程的综合，不是两个数相乘。而且同一个 mAP 可以对应完全不同的 P/R 组合 |
| 数据里全是缺陷，Precision 就是 100% | P 的分母是"模型报出来的框数"，不是"图里缺陷数"。**报得越多、错的越多，P 越低**。全缺陷数据只会让 Recall 的分母确定，不影响 Precision |
| DQN 能把 p95 从 540ms 压到 60ms | p95 是**阶梯函数**，由上云比例决定：上云比例 > 5%，p95 必然在 540ms 那一档。**任何算法都改不了这条物理规律**，只能改"上云比例" |
| 高分辨率复检 = 看得更清 | 原图只有 200×200，放大到 960 是**插值**，没有新信息。真正的收益叫 **尺度归一化**：把目标摆到画面正中占比更大，让它在特征图上占更多格子 |
| 放大整图会改变框和图的相对大小 | **不会，面积占比恒定不变**。变的是"目标在特征图上占几个格子"（绝对像素 ÷ stride），这两件事必须分开想 |

## 7. 一句话总纲（可以背下来）

> **延迟不能优化，只能定死（约束）；定死之后，问题变成"只有 5% 的复检名额，发给谁最划算"；而"划算"的定义不是"模型最没把握的"，是"最可能是误报或漏报的"。**

对应到指标：**在 FPPI 可接受的范围内，把 Recall 做到最高。**
